Redis에서 DB의 데이터의 변경에 맞추어 일관성을 유지할 필요가 있습니다. 앱 코드에서 두 저장소 모두에 write를 시도할 수 있지만 이럴 경우 DB에만 성공하고 Redis 쓰기는 실패 할 경우 일관성에 어긋나게 됩니다.

이를 해결하기 위해 Azure 환경에서 CDC(Change Data Cpature)로 Redis를 맞추는 구조에 대해서 알아보겠습니다.

![Untitled]({{ site.baseurl }}{{ page.url }}/img/cdc-arch.png)_CDC Pipeline_

**구성 요소 설명**

- PostgreSQL(DB): 변경을 WAL에 기록 publication으로 대상 테이블 지정
- Debezium(Pod): WAL을 읽어 JSON 이벤트로 변환
- Event Hub(Kakfa): Kafka 호환 리소스로 이벤트 수신, 발행
- redis-sync:(Spring): 이벤트를 수신하고 JSON 데이터를 처리
- Key Vault: 각종 비밀을 저장

### **Debezium**

Debezium은 DB 부하 없이 DB의 변경 사항을 손실 없이 이벤트로 발행하기 위해 아래의 개념을 사용합니다.

**WAL과 logical replication**

DB에서 데이터가 변경되면 이 내용을 WAL에 로그 형태로 기록합니다. DB 파라미터를 `wal_level=logical`로 설정한다면 어떤 테이블의 어떤 행이 바뀌었는지를 기록하는데 이를 debezium이 logical replication으로 읽어서 별도의 폴링 없이 이 정보를 받게 됩니다.

- > DB 부하 없이 정보 획득 가능

**Replication slot**

slot은 연결이 잠시 끊어져도 소비자가 어디까지 읽었는지를 확인하는 책갈피 같은 개념으로 나중에 slot 기준으로 다시 읽어야하기 때문에 DB는 slot 뒤의 WAL은 지우지 않고 계속 보존합니다. 이는 디스크 낭비로 이어질 수 있기에 언제나 신경써야합니다.

> *Debezium은 slot 기준 차례로 읽기에 1개의 Pod로 구성 되어야 한다.*
> 

**Heartbeat**

감시 대상 테이블에 변경이 없어도 모든 데이터는 WAL에 쌓입니다. 장시간 감시 대상 테이블에 변화가 없으면 과도하게 디스크에 적재되기에, hearbeat 테이블을 만들어 주기적으로 slot을 전진시켜 WAL를 삭제 시키도록 해야합니다.

이렇게 DB의 변경 사항을 JSON 이벤트로 변환하여 Event Hub(Kafka)로 전송합니다.

### **Event Hub(Kafka)**

사실 debezium에서 바로 Redis 또는 수신자 앱으로 전송할 수 있습니다. 하지만 아래 개념을 통해 중간 레이어를 추가하는 것도 검토 가능합니다.

**장애 격리**

수신자가 장애 상태이면 slot이 지연되고 이는 DB까지 장애가 확장될 수 있습니다.

**재처리 및 확장**

Redis나 뒤의 데이터가 오염되었다고 해도 오프셋을 조정해 새로운 Redis를 새로 만들 수 있으며 수신자가 여럿으로 확대가 가능하기도 합니다.

### **Redis Sync**

데이터를 수신받고 적절하게 가공하여 Redis에 저장하는 어플리케이션입니다.

일반적으로 Spring Boot를 통해 간단한 biz 로직까지 첨부하기도 합니다.

## **파이프라인 성능 테스트**

데이터 처리 파이프라인임으로 처리량을 미리 파악 얼마나 처리가 가능한지 확인해야합니다.

각 구간의 처리 시간을 측정하기 위해 각 레이어에서 시간 관련 파라미터를 아래와 같이 추출하고 이를 마지막 레이어인 redis-sync에서 Log로 출력하도록 했습니다.

**각 레이어에서 관련 시간 파라미터**

| 시각 | 위치 | 의미 |
| --- | --- | --- |
| `payload.source.ts_ms` | Debezium 메시지 | PG에서 커밋된 시각 |
| `payload.ts_ms` | Debezium 메시지 | Debezium이 처리한 시각 |
| `ConsumerRecord.timestamp()` | Kafka 레코드 | EH로 보낸 시각 |
| `System.currentTimeMillis()` | redis-sync | Redis에 쓴 직후 |

**구간별 시간 추정식**

```
dbz_ms  = payload.ts_ms - source.ts_ms     // PG → Debezium
eh_ms   = record.timestamp - payload.ts_ms // Debezium → EH
sync_ms = now - record.timestamp           // EH → Redis
e2e_ms  = now - source.ts_ms
```

**부하 테스트 용 쿼리**

```yaml
INSERT INTO target_table (id, type, value, memo, created_by, updated_by, updated_at)
SELECT 9300000000 + g, 'LOADTEST', 'lt-' || g, 'dbz load test', 'loadtest', 'loadtest', CURRENT_TIMESTAMP
FROM generate_series(1, 3000) g;
```

3000건의 데이터를 한번에 `INSERT` 한다.

**수행 결과 (redis-sync Log)**

![Untitled]({{ site.baseurl }}{{ page.url }}/img/cdc-asis.png)_redis-sync의 Pod Log_

redis-sync가 최종적으로 넘어온 시간을 출력했고 이걸 아래 표처럼 정리가 가능합니다

**값 정리**

| 항목 | 값 |
| --- | --- |
| E2E 최대 | 24,268ms |
| E2E 평균 | 19,878ms |
| PG → Debezium 평균 (`dbz_avg`) | 328ms |
| Debezium → EH 평균 (`eh_avg`) | 549ms |
| EH → Redis 평균 (`sync_avg`) | 19,000ms |
| EH → Redis 최대 (`sync_max`) | 22,996ms |
| 메시지 처리 간격 | 약 5ms |

PG → Debezium 구간 및 Debezium → EH는 평균 300~500ms로 초당 약 2400건을 처리하였습니다. 병목은 EH → Redis 구간으로 3000건을 약 19~22초에 처리합니다.

Event Hub(Kafka)의 Partition 4개로 구성되어 있지만 이를 처리하는 Thread는 1개며 Pod의 replica도 1개입니다.

**값 정리 및 이전과 비교**

다만 여전히 병복의 80%는 Consumer 앱인 redis-sync로 Redis 왕복 횟수 개선 또는 배치 리스너를 개선할 포인트가 남아 있습니다.

### 트러블 이슈 및 취약점 정보

**취약한 이미지**

`debezium/server:3.6.2.Final` 을 처음에 사용할려 했는데 CVE-2026-111497(Brotli 디코더 out-of-bounds write, CVSS 9.2)가 OS에 존재한다고 합니다.

이후에 나온 3.6.7은 이 취약점이 개선되어 있기에 해당 버전 이상을 사용하는것을 추천합니다.

**Consumer 앱 그룹이름 설정**

Spring kafka는 `@KafkaListener(id = ...)` 어노테이션에 `group id`를 명시하지 않으면 리스너 ID를 그룹 ID로 사용합니다. 리스너 ID를 자체적으로 명시하고 그룹 ID는 yml에 설정하였지만 이 동작으로 인해 리스너 ID의 그룹으로 접속하였습니다.

이 그룹에서는 일부 Consumer가 파티션을 점유하기도 하여 간헐적으로 하나의 Pod에서 파티션을 할당받지 못했습니다. 

### CDC의 도입 기준 및 트레이드 오프

Debezium을 통해 DB의 변경분을 읽는 파이프라인은 읽기가 많은 서비스에 DB 부하를 크게 줄여줍니다. 또한 상품에 대해 여러 제약과 연동이 있어 여러 경로에서 DB가 변경이 되는 경우 별도의 추가 로직 없이 모든 DB 변경 사항을 따라갑니다.

DB 반영에는 수 초 지연이 있을 수 있기에, 이를 허용할 수 있는 비즈니스 조건이 맞아야 합니다

예를 들어 조건이 많은 상품의 전시 정보가 있을 수 있습니다.

WAL와 Event hub을 통해 장애 상황에서도 재처리 및 이중 쓰기 방지에 장점을 보이나,  slot을 적절하게 관리해주지 않으면 DB 디스크 자체가 폭주할 수 있습니다 또한 서비스 관리 포인트가 추가되며 이를 위한 적절한 모니터링 구축이 필수적으로 따라옵니다.

정리하면 정확한 일관성을 보장하거나 대상 테이블의 개수가 적고 변경이 작으면 앱 레벨 캐시 또는 Outbox 패턴을 통해 별도 직접 앱에서 이벤트를 발행하는 방식을 먼저 검토하는 것이 낫습니다.
