과거 개발자의 역할이 좋은 코드를 작성하는 것에 집중되어 있었다면, 현재는 그 산출물을 직접 배포하고 운영하는 것까지 포함하는 DevOps 엔지니어로 그 역할이 확장되고 있다.

CKA를 취득하고 1년간 AKS 기반의 DevOps 업무를 하면서 경험한 내용을 함께 정리해보았다.

### CKA 취득 후기

CKA는 완전히 낯선 쿠버네티스를 처음 공부하기에 적절하다고 생각한다
체감상 Spring 보다 높은 추상도를 가진 쿠버네티스는 순전히 업무를 하면서 이해하기에는 조금 답답한 부분이 많을 것이라 생각한다. 

그에 따라 쿠버네티스 자체에 대한 이해를 높이기 위해서는 단순히 덤프 푸는 것이 아니라 

> https://www.udemy.com/course/certified-kubernetes-administrator-with-practice-tests/?srsltid=AfmBOor24Z5awvM9UOA9l10ufGv_PWajqCF_yE4rmkz4MC4aM7vJmiOe

이 인도 아저씨의 강의가 매우 큰 도움이 되었다.

특히나 강의초반에 Control Plane (Master Node)의 부분은 쿠버네티스가 어떤식으로 돌아가는지 이해를 정말 잘 시켜주는데 간략하게 정리하자면 아래와 같다.

**kube-apiserver:** Pod 생성부터 다른 작업의 결과 요청의 진입점 
**etcd**: k8s의 데이터베이스 오직 API Server와만 통신함 
**kube-scheduler**: Pod를 어느 Node로 배치할지?
**Kube-controller-manager**: 여러 Controller 모음(Nod, CronJob…)

위 기능들은 실제 업무에서는 클러스터를 처음부터 구축하는게 아니며 대부분은 EKS나 AKS 같은 관리형 클러스터를 사용하기에 실제로 업무에서 크게 설정을 할일은 없을것이라 판단된다. 

대부분의 개발자들은 Woker Node에서 활동하는데 뭄바스 아저씨는 Woker Node 영역또한 상당히 자세하게 설명을 해준다. 

**kubelet**: worker node 대장으로 pod 생성 및 ControlPlane에 상태보고
**kube-proxy**: woker node 라우팅 담당
**Conainer Runtime**: 컨테이너 실행 담당

그외에.. 쿠버네티스 내의 다양한 리소스들의 이론도 설명해주는데.. 상당히 도움이 된다.

### CKA와 실무 쿠버네티스(관리형 쿠버네티스)

실무에서 쿠버네티스를 직접 구축하고 사용하는 케이스는 적을것이라 판단된다.
`kubeadm`으로 구축 하는 경우도 적을 뿐만 아니라 AWS의 EKS나 Azure의 AKS를 주로 사용하는게 대부분이다. 

![image.png]({{ site.baseurl }}{{ page.url }}/img/manage_k8s.png.png)

이런 관리형 쿠버네티스(AKS 기준)는 어떤점이 다른지도 알아 보겠다.

실제 마스터 노드인 ControlPlane은 기본적으로 **블랙박스**이다. 
실제 사용자는 워커 노드에만 접속이 가능하며, 해당 Node의 관리만 가지고 있다.

**AKS - System Pool과 User Pool의 차이?** 

Systempool은 Control Plane과 통신하는 사이드 데몬들이 가동되어진다.

kube-proxy      → 각 노드에서 iptables 관리
CoreDNS         → Pod DNS 해석
Azure CNI       → 네트워크 할당
metrics-server  → HPA용 메트릭 수집

taint를 통해 운영 Pod들이 해당 Node에서는 기동될 수 없도록 조정되어 있다.

**Control Plane과 어떻게 통신할까?**

고객용 Woker Node와 관리형 Master Node는 완전히 다른 물리적 위치에 있기에 별도의 DNS 기반 통신이 필요하다. 

이 DNS 정보는 별도의 DNS Zone (Azure Private DNS Zone에서 관리되고 있으며 kubelet이 DNS 질의를 통해 담당하는 Controlplane을 찾아갈 수 있게 도움을 준다.

 **그렇다면 실무에 있어서는 쿠버네티스의 지식이 필요 없을까?**

관리형 쿠버네티스는 Control Plane 운영(etcd 관리, 인증서 갱신, 업그레이드 등)을 클라우드 공급자가 담당하므로, 해당 영역의 직접적인 지식은 필요 없을 수 있다.

하지만 Control Plane 위의 Worker Node 영역은 전적으로 사용자의 책임이며, 장애 발생 시 디버깅 및 원인 분석은 쿠버네티스 내부 동작 원리에 대한 이해 없이는 불가능하다고 생각한다. 

Pod의 생명주기 관리, requests/limits를 통한 리소스 최적화, PV/PVC를 활용한 스토리지 설계, RBAC 및 Secret 관리 등은 관리형 환경일지라도 동일하게 적용되는 지식이다.

결국 CKA에서 배운 쿠버네티스의 내부 동작 원리는 관리형 환경에서도 여전히 유효하다. 

Control Plane이 블랙박스로 가려져 있어도, 장애 상황에서 "왜 kubelet이 API Server를 못 찾는가", "왜 Pod가 Pending 상태인가"를 추적하는 능력은 결국 그 원리에 대한 이해에서 나온다.

1년간 AKS를 운영하면서 느낀 것은, 관리형 쿠버네티스는 운영의 부담을 줄여줄 뿐이지 쿠버네티스 지식 자체를 대체하지는 않는다는 것이다. 

오히려 추상화된 레이어 뒤에서 무슨 일이 일어나는지 알고 있는 사람과 모르는 사람의 차이는 장애 상황에서 극명하게 드러난다.

DevOps를 시작하는 분들께는 단순히 시험 합격이 목적이 아니라, 쿠버네티스가 어떻게 동작하는지를 이해하는 도구로서 CKA를 활용하길 권장한다.
